# SkyOps Intelligence — 최종 발표 Q&A 예상 질문 30개

---

## A. 프로젝트 개요 (1~5)

**Q1. 왜 항공 관제 분야를 선택했나요?**
> 항공편 지연으로 인한 경제적 손실이 연간 수조 원에 달하지만, 현재 대부분의 시스템이 배치 기반이라 실시간 대응이 어렵습니다. AI + 실시간 스트리밍 기술을 결합하면 관제사의 의사결정을 즉각 지원할 수 있다고 판단했습니다.

**Q2. 1인 프로젝트인데 이 규모를 어떻게 소화했나요?**
> 15주 스프린트를 Phase 1(파이프라인), Phase 2(AI 모델링), Phase 3(서빙+대시보드)로 나눠 매주 명확한 산출물을 정의했습니다. 오픈소스 생태계(Kafka, vLLM, LangChain, Next.js)를 적극 활용하여 핵심 로직에 집중했습니다.

**Q3. 실제 공항에서 사용할 수 있나요?**
> 현재는 PoC(개념 증명) 단계입니다. 실제 도입 시에는 항공안전법 준수, 관제사 인증, 데이터 보안 검증이 필요합니다. 본 시스템은 "자문 전용(Advisory Only)" 모드로 설계하여 최종 판단은 관제사가 수행합니다.

**Q4. 경쟁 서비스나 유사 연구가 있나요?**
> FlightAware, Cirium 등 상용 서비스가 있지만, 이들은 지연 예측에 집중하며 도메인 특화 LLM 기반 자연어 설명 기능은 제공하지 않습니다. 학술 연구에서도 ADS-B + LLM + RAG를 결합한 통합 시스템은 본 프로젝트가 최초 시도입니다.

**Q5. 프로젝트의 가장 큰 기술적 도전은 무엇이었나요?**
> RTX 3070 8GB라는 제한된 GPU에서 7B 파라미터 LLM을 학습(QLoRA, 9시간)하고 서빙(AWQ 4-bit)하는 것이 가장 큰 도전이었습니다. 메모리 최적화, 양자화, KV 캐시 튜닝 등 다양한 기법을 적용했습니다.

## B. 데이터 파이프라인 (6~10)

**Q6. OpenSky API의 데이터 정확도는 어떤가요?**
> OpenSky Network는 전 세계 30,000+ ADS-B 수신기로 구성된 공개 네트워크입니다. 위치 정확도는 약 10m 수준이며, 한국 영공에서는 30초 폴링으로 60~80대의 항공기를 추적합니다. 군용기 등 ADS-B 미장착 기체는 감지 불가합니다.

**Q7. Kafka를 선택한 이유는? RabbitMQ나 Redis Streams와의 차이는?**
> Kafka는 높은 처리량(throughput)과 파티션 기반 병렬 처리, 그리고 데이터 재처리(replay)가 가능합니다. 항공 데이터는 시간 순서가 중요하고, 장애 시 재처리가 필요하므로 Kafka가 적합합니다. RabbitMQ는 메시지 라우팅에, Redis Streams는 경량 스트리밍에 적합하지만 내구성(durability)이 Kafka보다 낮습니다.

**Q8. PyFlink을 사용한 이유는? Apache Flink Java 버전과의 차이는?**
> PyFlink은 Python 생태계(pandas, scikit-learn)와의 통합이 용이합니다. Java Flink이 성능은 우수하지만, ML 모델 연동과 개발 속도 면에서 PyFlink이 1인 프로젝트에 적합했습니다. 실제로는 Kafka Consumer + 수동 윈도우 집계로 구현하여 Flink 의존성을 줄였습니다.

**Q9. Redis의 TTL 600초 설정 근거는?**
> 항공기가 한국 영공을 통과하는 평균 시간이 약 30~60분입니다. 10분(600초) TTL은 최근 활성 항공기만 유지하면서 메모리를 효율적으로 관리하기 위한 설정입니다. 지상 대기 중인 항공기도 포함하려면 TTL을 늘릴 수 있습니다.

**Q10. 실시간 파이프라인의 End-to-End 지연 시간은?**
> OpenSky API 폴링(30초) → Kafka 전송(~100ms) → Flink 처리(~200ms) → Redis 저장(~5ms) → WebSocket push(3초) 기준으로, 최대 약 33초의 지연이 발생합니다. 이는 관제 보조 목적으로는 충분합니다.

## C. AI 모델 (11~17)

**Q11. XGBoost RMSE가 24.64분인데, 목표 15분에 미달한 이유는?**
> 주요 원인은 세 가지입니다: (1) Kaggle 미국 국내선 데이터로 한국 공항 특성이 미반영, (2) 실시간 기상 데이터가 직접 Feature로 포함되지 않음, (3) 지연 분포의 극단적 비대칭성(대부분 0~5분, 소수 60분+)으로 RMSE가 이상치에 민감합니다. 분류 정확도 88.3%는 목표(75%)를 크게 초과했습니다.

**Q12. Isolation Forest F1이 0.335인데 왜 이렇게 낮나요?**
> Isolation Forest는 비지도 학습이므로 레이블 없이 이상치를 탐지합니다. 평가 시 사용한 레이블의 품질이 불확실하고, contamination 5% 설정이 실제 이상 비율과 불일치할 수 있습니다. CEP 룰 엔진과 앙상블하여 실시간에서는 효과적으로 이상을 감지합니다.

**Q13. SHAP 분석에서 가장 의미 있는 발견은?**
> Cascade Delay 효과입니다. 직전편 도착 지연(prev_arr_delay_min, SHAP 2.93분)이 체인처럼 전파되는 패턴을 정량적으로 확인했습니다. 이는 공항 운영에서 "지연 전파 차단"이 핵심 전략임을 시사합니다.

**Q14. Feature 20개는 어떤 기준으로 선정했나요?**
> 항공 운항 도메인 지식 기반으로 5개 그룹(시간, 노선, 이력, 혼잡, 기상)에서 선정했습니다. Optuna 최적화 후 SHAP으로 검증하여 dep_dayofyear, prev_arr_delay_min, route_hist_delay가 상위 3개 Feature로 확인되었습니다.

**Q15. CEP 룰의 임계값(152m/30초)은 어떤 근거인가요?**
> FAA AIM 기준 정상 상승/하강률은 약 500ft/분(약 152m/30초)입니다. 이를 초과하는 고도 변화를 이상으로 판정합니다. 심각도는 기준치 대비 초과 비율로 LOW(1~1.5배), MEDIUM(1.5~2배), HIGH(2배+)로 분류합니다.

**Q16. 5-Fold CV와 Test Set 성능 차이가 큰 이유는?**
> CV RMSE 32.18분 vs Test RMSE 36.59분의 차이는 시간적 분포 변화(temporal shift)에 기인합니다. 랜덤 분할 대신 시간 기반 분할(Time Series Split)을 적용하면 더 현실적인 평가가 가능합니다.

**Q17. 모델 업데이트 주기와 재학습 전략은?**
> Airflow DAG으로 일 1회 자동 재학습을 스케줄링합니다. EvidentlyAI 드리프트 감지 모듈이 Feature 분포 변화를 모니터링하고, 드리프트 감지 시 자동으로 재학습을 트리거합니다.

## D. LLM (18~24)

**Q18. OpenAI API 쓰면 되는데 왜 자체 LLM을 만들었나요?**
> 세 가지 이유입니다: (1) 데이터 보안 — 항공 관제 교신은 기밀이므로 외부 서버 전송 불가, (2) 오프라인 운용 — 네트워크 장애 시에도 작동해야 함, (3) 도메인 정확도 — 범용 LLM은 ATC 전문 용어와 절차를 정확히 모릅니다.

**Q19. Qwen2.5를 선택한 이유는? Llama 3.1 대신?**
> 원래 Llama 3.1 8B를 계획했으나, HuggingFace 게이트 모델이라 HF_TOKEN이 필요하고 RTX 3070 8GB에서 메모리 이슈가 있었습니다. Qwen2.5-7B는 공개 모델이고 8GB VRAM에서 안정적으로 학습 가능했습니다.

**Q20. QLoRA에서 LoRA rank=64를 선택한 이유는?**
> rank가 높을수록 표현력이 증가하지만 메모리 사용도 증가합니다. rank=16/32/64를 비교 테스트한 결과, rank=64에서 Train Loss 수렴이 가장 빨랐고 8GB VRAM 내에서 안정적으로 학습 가능했습니다. 학습 파라미터는 전체의 약 0.92%(40M/4.4B)입니다.

**Q21. DPO가 SFT 대비 실제로 개선된 점은?**
> Eval Loss가 SFT 0.0445 → DPO 0.0294로 34% 개선되었습니다. rewards/accuracies가 step 20부터 100%에 도달하여 chosen/rejected 판별이 완벽해졌고, margins가 0.80→8.91로 확대되어 선호 응답과 비선호 응답의 격차가 명확해졌습니다.

**Q22. LLM이 중국어를 섞어서 답변하는 문제는 어떻게 해결했나요?**
> Qwen2.5의 기본 언어가 중국어이기 때문에 발생합니다. (1) System Prompt에 "중국어 절대 금지" 명시, (2) 영어 키워드를 한국어로 변환 후 전달, (3) `_clean_korean()` 후처리 필터로 중국어 비율 30% 이상인 줄을 제거합니다. 근본적 해결은 한국어 특화 모델(SOLAR, KULLM)로 전환이 필요합니다.

**Q23. ROUGE-L 0.169가 낮아 보이는데 괜찮나요?**
> 생성형 LLM 평가의 특성상 BLEU/ROUGE는 절대값이 낮게 나옵니다. 같은 의미를 다른 어휘로 표현해도 낮은 점수가 나오는 n-gram 매칭의 한계입니다. 보다 정확한 평가를 위해 BERTScore나 LLM-as-Judge(GPT-4 평가) 도입을 권장합니다.

**Q24. RAG에서 ChromaDB를 선택한 이유는?**
> ChromaDB는 Python 네이티브, 로컬 파일 기반으로 설치가 간편하고, LangChain과의 통합이 원활합니다. Pinecone이나 Weaviate는 클라우드 의존성이 있어 오프라인 운용에 부적합합니다. 임베딩 모델은 BAAI/bge-m3으로 다국어(한/영) 검색을 지원합니다.

## E. 서빙 및 대시보드 (25~28)

**Q25. vLLM을 선택한 이유는? llama.cpp나 TGI와의 비교는?**
> vLLM은 PagedAttention으로 KV 캐시를 효율적으로 관리하고, OpenAI 호환 API를 기본 제공합니다. llama.cpp는 CPU 추론에 최적화되어 있고, TGI는 Hugging Face 종속성이 강합니다. AWQ 양자화 + awq_marlin 커널 조합으로 RTX 3070에서 최적 성능을 달성했습니다.

**Q26. WebSocket과 REST 폴링을 동시에 구현한 이유는?**
> WebSocket이 실시간성에서 우수하지만 네트워크 불안정 시 연결이 끊길 수 있습니다. SWR 폴링을 fallback으로 구현하여 WebSocket 연결 실패 시에도 5초 간격으로 데이터를 갱신합니다. Mock 데이터도 지원하여 오프라인 데모가 가능합니다.

**Q27. Next.js를 선택한 이유는? React SPA와의 차이는?**
> Next.js는 App Router 기반 파일 시스템 라우팅, SSR/SSG 지원, 빠른 개발 속도가 장점입니다. 대시보드 특성상 SEO는 불필요하지만, 코드 분할과 라우팅 구조가 6페이지 관제 대시보드에 적합했습니다.

**Q28. API 응답 시간 11ms는 어떻게 달성했나요?**
> XGBoost 모델을 싱글톤 패턴으로 메모리에 상주시키고, pickle 역직렬화를 서버 시작 시 1회만 수행합니다. 예측은 numpy 행렬 연산으로 처리되어 매우 빠릅니다. 반면 LLM 호출은 vLLM 추론 시간(3~5초)이 소요됩니다.

## F. 확장성 및 향후 계획 (29~30)

**Q29. 이 시스템을 실제 공항에 도입한다면 비용은?**
> 파일럿(3개월, 인천공항 1곳)에 약 5,000만 원(GPU 서버 + 설치 + 운영), 3개 공항 확장(6개월)에 약 2억 원으로 추산합니다. 오픈소스 기반이라 라이선스 비용이 없고, GCP Cloud Run으로 확장 시 사용량 기반 과금입니다.

**Q30. 졸업 후 이 프로젝트를 어떻게 활용할 계획인가요?**
> 세 가지 방향을 고려합니다: (1) GitHub 포트폴리오로 MLOps/AI 엔지니어 취업 활용, (2) 논문 투고 (한국정보과학회 또는 항공우주학회), (3) 한국공항공사 또는 인천공항공사에 PoC 제안. 특히 QLoRA+DPO LLM 파인튜닝, Kafka 실시간 파이프라인, Next.js 대시보드 경험이 차별화 포인트입니다.
