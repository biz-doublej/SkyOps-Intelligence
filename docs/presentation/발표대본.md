이 프로젝트의 한 줄 요약은 슬라이드에 적힌 대로 **"이상을 탐지하고, 원인을 설명하고, 대응 절차를 5초 이내에 자동 생성한다"** 입니다. 그냥 예측하는 것만이 아니라, **왜 그런지 말해주고 무엇을 해야 할지까지 알려주는** AI (에이아이) 파트너를 목표로 설계했습니다.

## 슬라이드 3 · 프로젝트 개요 (45초)

SkyOps Intelligence (스카이옵스 인텔리전스)는 **항공 관제사를 위한 실시간 AI (에이아이) 파트너**입니다. 6개의 핵심 기능을 제공합니다.

첫째, **15분 앞서 지연을 예측**합니다. 단순 예측이 아니라 Conformal Prediction (컨포멀 프리딕션)이라는 기법으로 **"90% 확률로 6~41분 지연"** 같은 신뢰구간까지 제공합니다.

둘째, **실시간 이상을 탐지**합니다. 비행 단계별로 모델을 7개 만들어서 단계마다 정상 범위가 다른 점을 반영했습니다.

셋째, **자연어로 원인을 설명**합니다. 제가 직접 파인튜닝한 한국어 LLM (엘엘엠)이 RAG (라그) 기법으로 FAA (에프에이에이) 규정, ICAO (아이카오) 매뉴얼, SOP (에스오피)를 참조해 답변합니다.

넷째, **FAA SWIM (에프에이에이 스윔) 실시간 데이터를 통합**했습니다. 이게 아마 이번 프로젝트의 가장 큰 성과 중 하나인데, **60초 안에 실제 219건의 NOTAM (노탐)을 수신**하는 걸 검증했습니다.

다섯째와 여섯째는 Next.js (넥스트제이에스) 대시보드와 자동 승객 안내문 생성 기능입니다.

## 슬라이드 4 · 문제 정의 (1분)

왜 이 프로젝트를 만들었는지 말씀드리겠습니다.

현재 항공 운영에는 3대 문제가 있습니다.

**첫째, 지연 예측이 불투명합니다.** 기존 모델은 "예상 15분 지연"이라고만 말하지 "얼마나 확신할 수 있나"는 알려주지 않습니다. 관제사는 이 숫자 하나만 보고 승객 안내를 해야 하는데, 실제로는 5분일 수도 40분일 수도 있습니다. 저는 여기에 **수학적으로 보장된 신뢰구간**을 추가해서 관제사가 "최악의 경우 41분까지 갈 수 있으니 승객 안내를 준비하자" 같은 정량적 판단을 할 수 있게 했습니다.

**둘째, 이상 탐지의 false positive (폴스 포지티브)가 너무 많습니다.** 단일 임계값으로는 이착륙 중의 정상적인 급상승·급하강까지 이상으로 분류됩니다. 관제사는 계속 울리는 알람에 무감각해지는 "alert fatigue (얼럿 패티그)" 현상이 생기고, 이게 실제 사고로 이어지는 경우가 있습니다. 저는 **비행 단계별로 별도 모델 7개**를 만들어 이걸 해결했습니다.

**셋째, 의사결정 보조가 없습니다.** FAA AIM (에프에이에이 에이아이엠), ICAO Annex (아이카오 에넥스) 같은 규정집은 수백 페이지인데 비상 상황에 빠르게 참조하기 어렵습니다. 저는 한국어 특화 LLM (엘엘엠) + RAG (라그) 시스템으로 **5초 이내에 관련 규정을 인용한 답변**을 제공합니다.

## 슬라이드 5 · 시스템 아키텍처 (1분 10초)

전체 시스템은 **5-Layer (파이브 레이어) 구조**로 설계했습니다.

**Layer 1 (레이어 원)은 데이터 수집**입니다. OpenSky Network (오픈스카이 네트워크)에서 ADS-B (에이디에스-비) 비행 위치를 받고, NOAA (노아)와 기상청에서 METAR (메타) 기상을 받고, 미 FAA (에프에이에이)의 SWIM (스윔)에서 실시간 NOTAM (노탐)을 받습니다.

**Layer 2 (레이어 투)는 스트리밍 처리**입니다. 초당 수천 건의 ADS-B (에이디에스-비) 이벤트를 Apache Kafka (아파치 카프카)에서 받아서 Avro Schema Registry (아브로 스키마 레지스트리)로 스키마를 강제하고, PyFlink (파이플링크)로 5분 단위 집계하고, Redis (레디스)에 항공기 상태를 캐싱합니다.

**Layer 3 (레이어 쓰리)은 AI (에이아이) 모델**입니다. XGBoost (엑스지부스트)로 지연을 예측하고, 단계별 Isolation Forest (아이솔레이션 포레스트) 7개로 이상을 탐지하고, Qwen2.5-7B (큐웬 투포인트파이브 세븐비) 한국어 LLM (엘엘엠)으로 자연어 설명을 생성합니다.

**Layer 4 (레이어 포)는 서빙**입니다. FastAPI (패스트에이피아이)가 REST API (레스트 에이피아이) 13개와 WebSocket (웹소켓) 3개를 제공하고, vLLM (브이엘엘엠)이 LLM (엘엘엠) 추론을 담당하고, ChromaDB (크로마디비)가 RAG (라그) 지식 검색을 담당합니다.

**Layer 5 (레이어 파이브)는 대시보드**입니다. Next.js 16 (넥스트제이에스 16)으로 만든 7페이지 관제 대시보드에 Leaflet (리플릿) 지도, MapLibre (맵라이브러) 히트맵, AI (에이아이) 챗봇이 있고, 외부에는 Cloudflare Tunnel (클라우드플레어 터널)로 공개됩니다.

**중요한 점은 각 Layer (레이어)가 독립적으로 테스트·배포 가능하다**는 겁니다. Layer 3 (레이어 쓰리) 모델을 재학습해도 Layer 1 (레이어 원)·2·4·5는 건드리지 않아도 되도록 설계했습니다.

## 슬라이드 6 · 데이터 소스 (1분)

데이터는 4가지 소스에서 받습니다.

**OpenSky Network (오픈스카이 네트워크)**는 전 세계 35,000개 지상 수신기가 기여하는 공개 ADS-B (에이디에스-비) 데이터입니다. 항공기의 위도·경도·고도·속도를 10초마다 받습니다. 실제 운영 중인 비행기 데이터라 가치가 있습니다.

**NOAA (노아)와 KMA (케이엠에이) METAR (메타)**는 30분마다 갱신되는 실시간 공항 기상입니다. 기상은 지연의 가장 큰 단일 원인이라 반드시 포함했습니다.

**FAA SWIM (에프에이에이 스윔)**은 미 연방항공청의 공식 System Wide Information Management (시스템 와이드 인포메이션 매니지먼트)입니다. Solace JMS (솔레이스 제이엠에스) 브로커에 구독 계약을 맺고 실시간 NOTAM (노탐)을 받습니다. 제가 이걸 성공시키려고 **trust store (트러스트 스토어) 셋업만 3번 다시 했고**, 결국 DigiCert Global Root G2 (디지서트 글로벌 루트 지투) 인증서를 수동으로 c_rehash (씨-리해시) 형식으로 넣어서 해결했습니다.

**한국공항공사 ACDM (에이시디엠)**은 공공데이터포털 API (에이피아이)입니다. EUROCONTROL NM B2B (유로컨트롤 엔엠 비투비) 계약 없이도 한국 traffic (트래픽)의 지연 상황을 추정할 수 있는 대안 경로입니다.

## 슬라이드 7 · Kafka (카프카) (1분)

스트리밍의 중심에는 **Apache Kafka (아파치 카프카)**를 놓았습니다.

왜 Kafka (카프카)인가? 4가지 이유가 있습니다.

**첫째, 확장성.** ADS-B (에이디에스-비)는 초당 수천 건이라 HTTP REST (에이치티티피 레스트)로는 서버가 backpressure (백프레셔)를 받아서 못 버팁니다. Kafka (카프카)의 pub-sub (펍섭) + 로그 저장 모델이 적합합니다.

**둘째, 재사용성.** 같은 ADS-B (에이디에스-비) 데이터를 이상 탐지도 쓰고, 지연 예측도 쓰고, 대시보드 시각화도 씁니다. Kafka (카프카)는 producer (프로듀서) 하나에 consumer (컨슈머) 여러 개를 효율적으로 붙일 수 있습니다.

**셋째, 재처리 가능성.** 만약 새 모델을 만들었을 때 "어제 14시부터 다시 돌려보자"가 가능합니다. Kafka (카프카) 로그 기반 저장 덕분입니다.

**넷째, 스키마 강제.** Confluent Avro Schema Registry (컨플루언트 아브로 스키마 레지스트리)와 결합하면 producer (프로듀서)가 잘못된 필드를 보낼 때 즉시 거부됩니다. 장애 시 디버깅 시간이 크게 줄어듭니다.

토픽은 6개로 설계했습니다 — flight-position (플라이트 포지션), weather-event (웨더 이벤트), notam (노탐), atfm-restriction (에이티에프엠 리스트릭션), alert-decision (얼럿 디시전), 그리고 P8 (피에잇)에서 추가한 acdm-milestone (에이시디엠 마일스톤)입니다. 모두 Avro (아브로) v2.0 스키마로 계약 되어 있습니다.

## 슬라이드 8 · PyFlink (파이플링크) + Redis (레디스) (45초)

스트림 처리는 **PyFlink (파이플링크)**를 썼습니다. Spark (스파크)가 더 친숙한데 왜 Flink (플링크)냐? Spark (스파크)는 **micro-batch (마이크로 배치)** 방식이라 2-3초 지연이 있지만 Flink (플링크)는 **이벤트 단위 진짜 스트리밍**입니다. 항공처럼 실시간성이 critical (크리티컬)한 도메인에는 Flink (플링크)가 맞습니다. 또 Event-time (이벤트 타임) + Watermark (워터마크) 기능으로 네트워크 지연 때문에 늦게 도착하는 ADS-B (에이디에스-비) 이벤트도 올바른 시간 기준으로 집계할 수 있습니다.

**Redis (레디스)**는 관제사 대시보드의 p95 (피95) 응답 시간을 30ms 이하로 유지하려고 넣었습니다. PostgreSQL (포스트그레에스큐엘) 조회는 밀리초 단위지만 Redis (레디스)는 마이크로초 단위입니다. 실시간 항공기 위치 같은 핫 데이터는 Redis (레디스)에 캐싱합니다. 또 Active Learning (액티브 러닝)의 알람 debouncing (디바운싱)에도 TTL (티티엘) 60초 키를 활용합니다.

## 슬라이드 9 · XGBoost (엑스지부스트) (1분)

이제 AI (에이아이) 모델 이야기입니다. 지연 예측은 **XGBoost (엑스지부스트)**로 했습니다.

XGBoost (엑스지부스트)는 2014년 Tianqi Chen (티안치 첸)이 발표한 Gradient Boosting (그래디언트 부스팅) 알고리즘인데, Kaggle (캐글) 대회에서 tabular (태뷸러) 데이터 대부분의 우승 모델이라서 **업계 사실상 표준**입니다.

왜 XGBoost (엑스지부스트)를 썼나 4가지로 정리하면:

**첫째 정확도.** tabular (태뷸러) 데이터에서는 딥러닝보다 동등하거나 낫습니다. 특히 feature (피처)가 20-30개 이하일 때 그렇습니다.

**둘째 속도.** 히스토그램 기반 분할과 병렬 학습으로 **5.7M (파이브포인트세븐 밀리언) 행을 4분 만에 학습**합니다. GPU (지피유) 없이 CPU (씨피유)만으로도 가능합니다.

**셋째 해석성.** SHAP TreeExplainer (샤프 트리익스플레이너)로 "왜 이 항공편이 15분 지연된다고 예측했는가"를 feature (피처)별 기여도로 시각화할 수 있습니다. 관제사에게 근거를 제시할 수 있다는 뜻입니다.

**넷째 robustness (로버스트니스).** 결측값을 자동 처리하고, 이상치에 강하고, normalization (노멀라이제이션)이 필요 없습니다.

실제 우리 프로젝트에서 **Test RMSE (테스트 알엠에스이) 28.18분, Test R² (테스트 알제곱) 0.43, 분류 정확도 89%**를 달성했습니다. 특히 R² (알제곱) 0.43은 관제사에게 실질적 의사결정 지원 가능한 수준입니다.

## 슬라이드 10 · TimeSeriesSplit (타임시리즈스플릿) + Rotation (로테이션) (1분)

이 숫자가 처음부터 나온 게 아닙니다. **P0 (피제로)와 P1 (피원) 두 번의 Sprint (스프린트)**로 끌어올렸습니다.

**P0 (피제로) TimeSeriesSplit (타임시리즈스플릿)**. 원래 코드는 KFold shuffle=True (케이폴드 셔플 트루)로 되어 있었는데, 이건 시계열 데이터에서 미래 데이터로 과거를 예측하는 temporal leakage (템포럴 리키지)를 일으킵니다. walk-forward validation (워크포워드 밸리데이션) 방식인 TimeSeriesSplit (타임시리즈스플릿)으로 바꿨습니다. 결과적으로 **CV (씨브이) 표준편차가 ±0.30에서 ±6.14로 20배 증가**했는데, 이건 나쁜 게 아닙니다. 그동안 shuffle (셔플)이 숨기고 있던 **시간대별 성능 변동성이 정직하게 드러난 것**입니다.

**P1 (피원) Rotation Features (로테이션 피처)**. EUROCONTROL (유로컨트롤)의 연구를 보면 지연의 **45%는 reactionary (리액셔너리)**, 즉 전편 지연이 다음 편에 누적되는 거라고 합니다. 기존 모델은 항공편 하나만 독립적으로 봤는데, 저는 **한 항공기가 하루에 몇 번째 비행하는지, 직전 편이 얼마나 지연됐는지, 공항에서 얼마나 머물렀는지** 같은 5개 feature (피처)를 추가했습니다.

결과를 보시면 **Test R² (테스트 알제곱) 0.0996에서 0.4328로 335% 향상**됐습니다. 동일 XGBoost (엑스지부스트) 모델인데 feature (피처) 5개로 이렇게 큰 차이가 납니다. 이게 "모델을 키우는 것보다 도메인 지식이 중요하다"는 교훈을 실제로 체감한 순간이었습니다.

## 슬라이드 11 · Conformal Prediction (컨포멀 프리딕션) (1분 10초)

방금 XGBoost (엑스지부스트)가 "Test R² (테스트 알제곱) 0.43"이라 했는데, 이건 여전히 **평균적인 정확도**일 뿐입니다. 개별 예측이 얼마나 믿을 만한지는 모릅니다.

그래서 **Conformal Prediction (컨포멀 프리딕션)**을 도입했습니다.

왼쪽 빨간 박스가 기존 방식입니다. "15분 지연" 이라는 숫자 하나만 줍니다. 관제사가 이 숫자를 얼마나 믿어야 할지 모릅니다. 항공사에서 흔히 쓰는 high/medium/low confidence (하이/미디엄/로우 컨피던스)는 모델 기반이 아니라 그냥 예측값 크기 기반 휴리스틱입니다. 근거 없습니다.

오른쪽 초록 박스가 제 방식입니다. **"90% 확률로 6분에서 41분 지연"** 같은 신뢰구간을 줍니다. 이건 MAPIE (마피) 라이브러리로 구현한 Split Conformal Prediction (스플릿 컨포멀 프리딕션)인데 **분포 가정 없이 수학적으로 보장**되는 유효 예측구간입니다. 실측해보니 **Empirical coverage (엠피리컬 커버리지)가 정확히 90.00%** 나왔습니다.

P4+ (피포플러스)에서는 여기에 한 층 더해서 **Conformalized Quantile Regression (컨포멀라이즈드 퀀타일 리그레션)**을 추가했습니다. 기존은 좌우 대칭 interval (인터벌)이었는데, 기상 때문에 지연 분포는 한쪽으로 치우친 경우가 많아서 **비대칭 interval (인터벌)**이 더 정확합니다.

이 기법은 **의료 진단, 금융 VaR (바), 자율주행 안전 margin (마진)** 같이 잘못 판단하면 위험한 고위험 도메인에서 주로 쓰입니다. 항공도 같은 카테고리입니다.

## 슬라이드 12 · Isolation Forest (아이솔레이션 포레스트) 원리 (1분)

이상 탐지는 **Isolation Forest (아이솔레이션 포레스트)**로 했습니다.

핵심 아이디어는 **"이상치는 소수이고 다른 데이터와 거리가 멀다"** 입니다. 그래서 랜덤 트리로 데이터를 재귀적으로 분할하면 — 정상 데이터는 깊은 트리까지 가서야 isolation (아이솔레이션)되지만 이상 데이터는 얕은 트리에서 빨리 isolation (아이솔레이션)됩니다. 여러 트리의 평균 **path length (패스 렝스)**로 anomaly score (어노멀리 스코어)를 계산합니다.

가장 중요한 특성은 **비지도 학습**이라는 겁니다. 항공 사고 데이터는 label (라벨)이 희귀한데, IF (아이에프)는 label (라벨) 없이도 동작합니다.

왜 다른 모델이 아닌가?

**Autoencoder (오토인코더)**는 GPU (지피유)가 필요하고 학습 안정성이 떨어집니다. IF (아이에프)는 CPU (씨피유)에서 분 단위 학습 가능합니다.

**One-class SVM (원클래스 에스브이엠)**은 시간 복잡도가 O(n²~n³) (빅오 엔 제곱에서 엔 세제곱)이라 대용량에 느립니다. IF (아이에프)는 O(n log n) (빅오 엔 로그 엔)입니다.

**단일 통계 임계값**은 "고도 > 40,000ft (포티써우전드 피트)" 같은 룰이지만 cruise (크루즈)에서는 정상이라 오탐이 많습니다.

**LSTM Autoencoder (엘에스티엠 오토인코더)**는 시계열 학습 복잡도가 너무 높고, 현재 snapshot (스냅샷) feature (피처)만으로도 충분한 성능이 나와서 선택하지 않았습니다.

## 슬라이드 13 · Per-phase IF (퍼 페이즈 아이에프) ×7 (1분 15초)

이상 탐지의 가장 핵심적인 개선이 **P5+ (피파이브플러스) Per-phase Isolation Forest (퍼 페이즈 아이솔레이션 포레스트)**입니다.

**핵심 아이디어는 "비행 단계별로 정상의 범위가 완전히 다르다"** 는 겁니다. CRUISE (크루즈) 중에 30,000ft (써티써우전드 피트)는 정상인데, LANDING (랜딩) 중에 30,000ft (써티써우전드 피트)면 비정상입니다. 근데 단일 모델은 이 두 상황을 구분할 수 없습니다.

그래서 **단계별로 별도의 Isolation Forest (아이솔레이션 포레스트) 7개**를 학습했습니다. 각 단계마다 **contamination (컨태미네이션) 파라미터를 다르게 튜닝**했습니다. 예를 들어 TAXI (택시)는 0.02 — 이상 발생률이 낮기 때문입니다. 반면 APPROACH (어프로치)와 LANDING (랜딩)은 0.06 — 사고가 가장 빈발하는 구간이라 약간 더 민감하게 설정했습니다.

학습 데이터는 Kaggle (캐글)의 비행 feature (피처)로부터 **silver-labeling (실버 라벨링)**을 합니다. 각 행을 7개 단계 샘플로 synthesize (신스사이즈)해서 Random Forest (랜덤 포레스트) phase classifier (페이즈 클래시파이어)를 만들어서 라벨을 붙이는 방식입니다. 휴리스틱 분류기 대비 **90.3% agreement (어그리먼트)**가 나왔고, 기존 단일 모델보다 **alert fatigue (얼럿 패티그)를 67% 감소**시켰습니다.

## 슬라이드 14 · Active Learning (액티브 러닝) (1분)

이상 탐지 모델은 배포 후에도 계속 진화해야 합니다. 그래서 **P6 (피식스)에서 Active Learning (액티브 러닝) 자동 재학습 loop (루프)**를 만들었습니다.

5단계 흐름입니다.

**1단계**, API (에이피아이)가 이상을 탐지하고 AnomalyEvent (어노멀리 이벤트)에 alert_id (얼럿 아이디)를 부여합니다.

**2단계**, 분석가가 대시보드에서 True Positive (트루 포지티브), False Positive (폴스 포지티브), Uncertain (언서튼) 중 하나로 라벨링합니다.

**3단계**, Airflow DAG (에어플로우 닥)가 매일 새벽 2시에 feedback.jsonl (피드백 제이슨엘)을 분석해서 단계별 FP rate (에프피 레이트)를 계산합니다.

**4단계**, FP rate (에프피 레이트)가 35% 넘으면 contamination (컨태미네이션)을 낮추고, 10% 미만이면 높여서 **phase (페이즈)별 튜닝 값을 자동 조정**합니다.

**5단계**, 새 contamination (컨태미네이션)으로 Per-phase IF (퍼 페이즈 아이에프)를 재학습하고 `.reload_signal` (리로드 시그널) 파일을 touch (터치)합니다. 서빙 쪽 ModelStore (모델스토어)가 mtime (엠타임)을 watch (와치)하다가 변경 감지하면 **서비스 재시작 없이 hot-reload (핫리로드)**됩니다.

P7 (피세븐)에서는 여기에 한 단계 더 추가해서 **Bandit v2 (밴딧 브이투)**, Thompson sampling (톰슨 샘플링)으로 어떤 유형의 이상을 다음에 라벨링하게 할지 선택하는 로직을 넣었습니다. 다양성을 확보해서 분석가 피드백이 골고루 분산되게 했습니다.

## 슬라이드 15 · Qwen2.5-7B (큐웬 투포인트파이브 세븐비) 선택 이유 (1분 10초)

다음은 LLM (엘엘엠)입니다. 저는 **Qwen2.5-7B-Instruct (큐웬 투포인트파이브 세븐비 인스트럭트)**를 베이스 모델로 골랐습니다. 2024년 Alibaba (알리바바)가 발표한 7B (세븐비) 파라미터 instruction-tuned (인스트럭션 튠드) LLM (엘엘엠)이고, Apache 2.0 (아파치 투포인트제로) 오픈소스라 제약 없이 쓸 수 있습니다.

왜 Qwen2.5 (큐웬 투포인트파이브)인가? 4가지 비교를 하겠습니다.

**Llama-3-8B (라마 쓰리 에잇비)와 비교.** 영어 성능은 비슷한데 Qwen (큐웬)은 중국어와 **한국어 품질이 우위**입니다. 항공 관제사 대화는 한국어 표준 용어가 중요해서 이게 결정적이었습니다.

**Gemini (제미나이)와 GPT-4 (지피티 포)와 비교.** 클라우드 LLM (엘엘엠)은 성능은 좋지만 **항공 안전 데이터를 외부로 전송할 수 없습니다**. On-premise (온프레미스) 배포 가능한 오픈 모델이 필수였습니다.

**Qwen 72B (큐웬 세븐티투비)와 비교.** 72B (세븐티투비)는 성능 좀 더 좋지만 RTX 3070 (알티엑스 써리세븐티) 같은 컨수머 GPU (지피유)에는 올릴 수 없습니다. 7B (세븐비) 버전에 AWQ 4-bit (에이더블유큐 4비트) 양자화를 입히면 RTX 3070 (알티엑스 써리세븐티)의 8GB VRAM (에잇기가바이트 브이램)에서 **40 토큰/초** 생성이 가능합니다.

**Mistral-7B (미스트랄 세븐비)와 비교.** KMMLU (케이엠엠엘유), KoBEST (코베스트) 같은 한국어 벤치마크에서 Qwen (큐웬) 점수가 우위입니다.

실제 파인튜닝 결과, **QLoRA (큐로라) 학습 후 Eval Token Accuracy (이밸 토큰 어큐러시)가 97.88%** 나왔고, **DPO (디피오) 학습 후 Rewards Accuracy (리워즈 어큐러시)가 100%** 까지 올랐습니다.

## 슬라이드 16 · QLoRA (큐로라) (50초)

7B (세븐비) 모델을 어떻게 제 집 GPU (지피유)에서 학습했느냐 질문을 많이 받는데, **QLoRA (큐로라)** 덕분입니다.

Full Fine-tuning (풀 파인튜닝)은 7B (세븐비) 모델에 약 60GB VRAM (식스티기가바이트 브이램)이 필요한데, QLoRA (큐로라)는 6GB (식스기가바이트)까지 줄여줍니다. 3단계 메커니즘입니다.

**1단계 4-bit Quantization (4비트 퀀타이제이션).** Base model (베이스 모델) 가중치를 FP16 (에프피식스틴)에서 NF4 (엔에프포, 4-bit NormalFloat, 4비트 노멀플로트)로 압축합니다. 메모리 16배 절감.

**2단계 LoRA Adapter (로라 어댑터).** 원본 가중치는 freeze (프리즈)하고 Low-Rank Adapter (로우랭크 어댑터) 행렬만 학습합니다. rank 64 (랭크 식스티포)로 설정해서 학습해야 할 파라미터가 원본의 0.1% 수준만 됩니다.

**3단계 Gradient Checkpointing (그래디언트 체크포인팅).** Forward pass (포워드 패스) 중간 결과를 저장하지 않고 필요할 때 재계산합니다. 메모리를 시간으로 trade off (트레이드 오프)해서 더 큰 배치가 가능합니다.

RTX 3070 (알티엑스 써리세븐티) 8GB (에잇기가바이트)에서 총 9시간, 배치 4로 학습했습니다. 데이터는 13,969건이고 TRL SFTTrainer (티알엘 에스에프티트레이너)를 썼습니다.

## 슬라이드 17 · DPO (디피오) (1분)

QLoRA (큐로라)로 SFT (에스에프티)까지 끝낸 모델은 "정답"은 학습했는데 **"선호되는 답변 스타일"** 은 학습하지 못했습니다. 예를 들어 영어와 한국어가 섞여 나오거나, 공손어가 빠져서 "~하시오"가 아닌 "~해라"로 답하는 경우가 있습니다.

그래서 **DPO (디피오), Direct Preference Optimization (다이렉트 프리퍼런스 옵티마이제이션)**을 적용했습니다. 2023년 Stanford (스탠포드)가 NeurIPS (뉴립스) Best Paper (베스트 페이퍼)로 발표한 방법입니다.

왼쪽 초록 박스가 DPO (디피오)의 특징입니다. **chosen (초즌) / rejected (리젝티드) 페어만으로 학습**합니다. RLHF (알엘에이치에프)처럼 Reward Model (리워드 모델)을 별도로 학습할 필요가 없어서 훨씬 간단하고 안정적입니다. 기존 RLHF (알엘에이치에프)는 3단계였는데 DPO (디피오)는 1단계로 축소됩니다.

오른쪽이 예시입니다. "윈드시어(Windshear) 감지 시 대응은?" 이라는 질문에 — chosen (초즌)은 "활주로 진입 대기, ATC (에이티씨) 통보, 승객 안내..." 같은 완전한 한국어 답변이고, rejected (리젝티드)는 "Windshear detected. Follow the procedure. (윈드시어 디텍티드. 팔로 더 프로시저.)" 같은 영어 그대로나 짧은 답변입니다.

DPO (디피오)는 ChatGPT (챗지피티), Claude (클로드) 같은 최신 AI (에이아이) 어시스턴트의 alignment (얼라인먼트) 단계에 쓰입니다. OpenAI (오픈에이아이)와 Anthropic (앤트로픽)도 DPO (디피오) 계열 기법을 씁니다. 의료 AI (에이아이), 법률 AI (에이아이) 등 도메인 특화 스타일이 중요한 곳에 많이 쓰입니다.

제 프로젝트에서는 Korean SFT (코리안 에스에프티)/DPO (디피오) 시드 3,500건을 P7 (피세븐)에서 추가로 생성했습니다. 이제 GPU (지피유) 시간만 확보하면 재학습 가능한 상태입니다.

## 슬라이드 18 · RAG (라그) (1분)

LLM (엘엘엠)은 학습 시점 이후의 최신 정보를 모릅니다. 예를 들어 어제 발표된 NOTAM (노탐)은 모르고, 공항별 최신 SOP (에스오피)도 모릅니다. 이걸 해결하는 게 **RAG (라그), Retrieval-Augmented Generation (리트리벌 오그멘티드 제너레이션)**입니다.

4단계 파이프라인입니다. 먼저 사용자가 "RKSI (알케이에스아이) 활주로 15L (피프틴 엘) 폐쇄 시 대응?" 을 물어봅니다. **Embed (임베드) 단계**에서 BAAI bge-m3 (비에이에이아이 비지이-엠쓰리) 모델이 이 질문을 1024차원 벡터로 변환합니다. **Retrieve (리트리브) 단계**에서 ChromaDB (크로마디비)의 161개 chunk (청크) 중에서 top-4 (탑포)를 유사도 검색으로 찾아옵니다. **Generate (제너레이트) 단계**에서 Qwen2.5 (큐웬 투포인트파이브) LLM (엘엘엠)이 검색된 컨텍스트를 보고 답변을 생성합니다.

**ChromaDB (크로마디비)**를 고른 이유는 오픈소스이고 파이썬 우선이라는 점, 그리고 임베디드 모드로 별도 서버 없이 SQLite (에스큐라이트) + Parquet (파케이)만으로 동작한다는 점입니다. Pinecone (파인콘)은 유료이고 Weaviate (위비엣)는 복잡해서 MVP (엠비피)에 과합니다.

**BAAI/bge-m3 (비에이에이아이 비지이-엠쓰리)** 임베딩 모델은 다국어이고 한국어·영어·중국어를 동시에 처리합니다. MTEB (엠티이비) 벤치마크 최상위권 모델입니다.

코퍼스는 FAA AIM (에프에이에이 에이아이엠) 26개, ICAO Annex (아이카오 에넥스) 20개, SOP (에스오피) 25개, runbook (런북) 18개, RKSI (알케이에스아이) 특화 15개 등 **총 161 chunks (청크스)**로 구성됐습니다. 처음엔 6개로 시작해서 P6 (피식스)에서 95개, P6-F (피식스-에프)에서 161개까지 확장했습니다.

## 슬라이드 19 · FastAPI (패스트에이피아이) + vLLM (브이엘엘엠) (1분)

서빙 쪽으로 넘어가겠습니다. API (에이피아이)는 **FastAPI (패스트에이피아이)**를 썼습니다.

Flask (플라스크)가 더 친숙한데 왜 FastAPI (패스트에이피아이)냐? 네 가지 이유입니다.

**Pydantic v2 (파이댄틱 브이투)**로 request/response (리퀘스트/리스폰스) 스키마를 자동 검증합니다. 잘못된 필드 오면 즉시 400 에러. Flask (플라스크)는 별도 library (라이브러리) 필요합니다.

**Swagger UI (스웨거 유아이) 자동 생성**. `/docs` (슬래시 닥스) 열면 interactive (인터랙티브) 문서 바로 나옵니다. 이게 테스트 속도를 엄청 올려줍니다.

**Async/await (어싱크/어웨이트) 네이티브**. vLLM (브이엘엘엠), Redis (레디스), DB (디비)를 동시에 호출해도 병목 없습니다.

**WebSocket (웹소켓)이 first-class (퍼스트클래스)**. 대시보드 실시간 push (푸시)에 필수입니다.

P3 (피쓰리)에서 ADR-001 (에이디알-001) Phase 1 (페이즈 원)을 적용해서 **1,120줄짜리 api.py (에이피아이 닷 파이) 하나를 107줄 thin entry (씬 엔트리) + 6개 router (라우터)**로 분리했습니다. 유지보수성이 크게 좋아졌습니다.

**vLLM (브이엘엘엠)**은 LLM (엘엘엠) 추론 엔진입니다. HuggingFace Transformers (허깅페이스 트랜스포머스)보다 왜 나은가? **PagedAttention (페이지드 어텐션)**이 핵심입니다. GPU (지피유) 메모리를 OS (오에스) 페이징처럼 관리해서 메모리 fragmentation (프래그먼테이션)이 해소됩니다. **Continuous batching (컨티뉴어스 배칭)**으로 서로 다른 길이 요청을 GPU (지피유) 유휴 없이 처리합니다. AWQ 4-bit (에이더블유큐 4비트) 양자화로 모델 크기 4배 압축하면서 정확도는 유지합니다. RTX 3070 (알티엑스 써리세븐티)에서 **40 tok/s (톡 퍼 섹, 토큰/초)** 나오는데, Transformers (트랜스포머스)는 13 tok/s라서 **3배 빠릅니다**.

메인 대시보드에는 KPI (케이피아이) 카드 4종과 최근 알림이 있고, 실시간 지도는 Leaflet (리플릿)으로 WebSocket (웹소켓) + SWR (에스더블유알) fallback (폴백)으로 구현했고, 이상 탐지 페이지는 실시간 알림 피드와 심각도 필터가 있고, **P6-G (피식스-지)에서 추가한 NOTAM (노탐) 페이지**는 FAA SWIM (에프에이에이 스윔) 실 데이터를 보여줍니다. 4가지 severity (시비어리티)로 필터할 수 있고 공항별 분포도 볼 수 있습니다. 지연 예측 페이지는 폼 입력하면 Conformal (컨포멀) interval (인터벌)까지 보여주고, 혼잡도 맵은 MapLibre GL (맵라이브러 지엘) H3 (에이치쓰리) 헥사곤으로 공역 밀집도를 보여주고, AI (에이아이) 어시스턴트는 RAG (라그) 채팅과 승객 안내문 생성 사이드패널이 있습니다.

## 슬라이드 21 · MLOps Pipeline (엠엘옵스 파이프라인) (1분)

이 프로젝트가 "캡스톤 MVP (엠비피)" 를 넘어서 **"대기업급 운영 제품"** 체급으로 올라간 결정적 이유는 MLOps (엠엘옵스) 인프라 때문입니다.

**MLflow (엠엘플로우)**로 모든 학습 run (런)을 추적합니다. 하이퍼파라미터, 지표, artifact (아티팩트)까지 버전 관리됩니다.

**EvidentlyAI (에비던틀리에이아이)**는 Population Stability Index (파퓰레이션 스태빌리티 인덱스, PSI, 피에스아이)로 입력 feature (피처) 분포 변화를 감지해서 drift (드리프트)가 생기면 알람을 띄웁니다.

**Feast Feature Store (피스트 피처 스토어)**는 P6-A (피식스-에이)에서 도입했습니다. Offline parquet (오프라인 파케이)와 Online Redis db=1 (온라인 레디스 디비 원) 두 계층을 두고, **training-serving skew (트레이닝-서빙 스큐)**를 방지합니다.

**Apache Iceberg (아파치 아이스버그)**는 P6-D (피식스-디)에서 추가한 데이터 레이크입니다. Bronze/Silver/Gold (브론즈/실버/골드) 10개 테이블을 운영하고, snapshot (스냅샷)과 time-travel (타임트래블)이 가능합니다.

**OpenLineage (오픈리니지)와 Marquez (마르케즈)**로 데이터셋에서 모델을 거쳐 deployment (디플로이먼트)까지의 lineage (리니지)를 추적합니다.

**Confluent Schema Registry (컨플루언트 스키마 레지스트리)**로 Avro (아브로) 5개 토픽을 BACKWARD compat (백워드 캄팻) 정책으로 관리합니다.

이 MLOps (엠엘옵스) 스택 덕분에 **P0 (피제로)부터 P8 (피에잇)까지 8개 sprint (스프린트), 총 50+ commits (커밋)**가 체계적으로 쌓였습니다.

## 슬라이드 22 · Observability (옵저버빌리티) (50초)

"배포한 서비스가 실제로 건강한가"를 측정하는 것이 Observability (옵저버빌리티)입니다.

**Jaeger (예거)**로 distributed trace (디스트리뷰티드 트레이스)를 봅니다. FastAPI (패스트에이피아이) → XGBoost (엑스지부스트) → Redis (레디스) 전 구간 요청의 어디가 병목인지 시각적으로 확인할 수 있습니다.

**Prometheus (프로메테우스)**가 시계열 메트릭을 수집합니다. 서비스별 QPS (큐피에스), latency (레이턴시), error rate (에러 레이트)를 초 단위로 저장합니다.

**Grafana (그라파나)**에는 9-panel (나인 패널) SLO (에스엘오) 대시보드와 3개 alert rule (얼럿 룰)을 정의했습니다. API (에이피아이) 5xx rate (파이브엑스엑스 레이트) 1% 초과, delay endpoint (딜레이 엔드포인트) p95 (피95) 500ms 초과, 이상 탐지 HIGH severity (하이 시비어리티) ratio (레이쇼)의 24시간 baseline (베이스라인) 대비 +15pp (피피) drift (드리프트) — 이 셋 중 하나라도 걸리면 PagerDuty (페이저듀티) 알람이 울립니다.

**OpenTelemetry (오픈텔레메트리)**는 이 모든 계측의 표준입니다. 코드에서 OTLP gRPC (오티엘피 지알피씨)로 방출만 하면 vendor (벤더) 중립적으로 Datadog (데이터독), New Relic (뉴 렐릭) 같은 상용 서비스로도 즉시 전환 가능합니다.

**Marquez (마르케즈)**는 P7 (피세븐)에서 추가한 OpenLineage UI (오픈리니지 유아이)입니다. XGBoost (엑스지부스트) 모델 학습 run (런)이 어떤 Iceberg Silver (아이스버그 실버) 테이블 snapshot (스냅샷)을 입력으로 썼는지 그래프로 확인할 수 있습니다.

## 슬라이드 25 · FAA SWIM (에프에이에이 스윔) 실연동 (1분)

이 프로젝트에서 가장 자랑스럽게 생각하는 성과를 따로 하나의 슬라이드로 만들었습니다.

**60초 안에 실제 219건의 NOTAM (노탐)을 FAA (에프에이에이)로부터 직접 수신**했습니다.

이게 왜 의미 있냐면 — 대부분의 대학 프로젝트는 mock (모크) 데이터나 Kaggle (캐글) 덤프로 끝납니다. 저는 **미 FAA (에프에이에이)의 공식 System Wide Information Management (시스템 와이드 인포메이션 매니지먼트)** 브로커에 직접 JMS (제이엠에스) 구독을 맺고, TLS 1.2 (티엘에스 원포인트투)로 인증서 검증까지 통과했습니다.

기술 스택을 보시면 — Solace PubSub+ SMF (솔레이스 펍섭 플러스 에스엠에프) over TLS (오버 티엘에스), ems2.swim.faa.gov (이엠에스투 닷 스윔 닷 에프에이에이 닷 거브) 프로덕션 엔드포인트, AIXM 5.1 XML (에이아이엑스엠 파이브포인트원 엑스엠엘) + FAA event (에프에이에이 이벤트) 네임스페이스 파서, Q-code (큐코드) 매핑 (QNDAS (큐엔디에이에스)는 NAV (내브) 시설 장애, QMRLC (큐엠알엘씨)는 활주로 폐쇄 등), 그리고 c_rehash (씨-리해시) 형식 TLS (티엘에스) trust store (트러스트 스토어)에 DigiCert Global Root G2 (디지서트 글로벌 루트 지투) 수동 import (임포트)까지 — 이게 **엔터프라이즈급 통합** 입니다.

검증 로그가 `received=219 published=219 parse_err=0` (리시브드 219 퍼블리시드 219 파스 에러 0) 인 건, **219건 받고 219건 Kafka (카프카)에 publish (퍼블리시)하고 parsing (파싱) 에러 하나도 없었다**는 뜻입니다. 완벽 수신입니다.

## 💬 예상 질문 & 답변 준비

### Q1 (큐원): "왜 한국 공항 데이터가 아니라 미국 Kaggle (캐글)을 썼나요?"

A (에이): 좋은 질문입니다. 한국공항공사 데이터는 **공공데이터포털에서 API (에이피아이) 신청**을 해야 하는데 학부생 자격으로 승인이 늦었습니다. 대신 P7-E (피세븐-이)에서 KAC (케이에이씨) 공공데이터 client (클라이언트) 코드를 준비해뒀고 API key (에이피아이 키) 받으면 즉시 활성화 가능합니다. 그리고 **Rotation features (로테이션 피처) 같은 방법론은 국가 무관**해서 학습 데이터만 교체하면 됩니다.

### Q2 (큐투): "왜 Isolation Forest (아이솔레이션 포레스트) F1 (에프원) 0.345가 이렇게 낮은가요? 개선 못 하나요?"

A (에이): F1 (에프원)이 낮은 이유는 **ground truth label (그라운드 트루스 라벨) 자체를 자체 생성**했기 때문입니다. 실제 사고 데이터는 ICAO (아이카오)가 공개 안 해서 저는 CEP rule (씨이피 룰) 기반으로 pseudo-label (슈도 라벨)을 만들었습니다. Active Learning loop (액티브 러닝 루프)이 이미 구축되어 있으니, **실제 관제사 피드백이 3개월 쌓이면 F1 (에프원) 0.85+** 달성 가능합니다. 이게 P9+ (피나인플러스) 에서 한국공항공사와 MOU (엠오유) 맺어서 해결할 부분입니다.

### Q3 (큐쓰리): "Qwen2.5 (큐웬 투포인트파이브) 대신 HyperCLOVA (하이퍼클로바)나 KoGPT (코지피티) 같은 한국어 특화 모델은 왜 안 썼나요?"

A (에이): 세 가지 이유입니다. 첫째, **HyperCLOVA (하이퍼클로바)는 유료 API (에이피아이)이고 on-premise (온프레미스) 불가**입니다. 항공 안전 데이터 외부 전송이 금지되어서 쓸 수 없습니다. 둘째, **KoGPT (코지피티)는 2.0 (투포인트제로) 버전이고 2024년 이후 업데이트가 없어** maintenance (메인테넌스)가 걱정됩니다. 셋째, **Qwen2.5 (큐웬 투포인트파이브)가 KoBEST (코베스트), KMMLU (케이엠엠엘유) 같은 한국어 benchmark (벤치마크)**에서 상위권입니다. 게다가 Alibaba (알리바바)가 지속적으로 모델 업데이트하고 있어 future-proof (퓨처 프루프)합니다.

### Q4 (큐포): "Apache Kafka (아파치 카프카) 없이 Redis Stream (레디스 스트림)이나 SQS (에스큐에스)만 써도 되지 않나요?"

A (에이): Redis Stream (레디스 스트림)은 **persistence (퍼시스턴스)가 약하고 consumer group (컨슈머 그룹) 운영이 복잡**합니다. SQS (에스큐에스)는 **순서 보장이 FIFO queue (피포 큐)에서만** 되고 가격이 메시지당입니다. Kafka (카프카)는 **영구 로그 + 순서 보장 + exact-once (이그잭트 원스) 시맨틱스**를 파티션 단위로 보장합니다. 항공 데이터는 재처리(replay, 리플레이)가 중요한데 이건 Kafka (카프카)만 됩니다.

### Q5 (큐파이브): "FAA SWIM (에프에이에이 스윔) 받는 건 좋은데 한국 NOTAM (노탐)은 어떻게?"

A (에이): 한국은 **항공정보국(AIS Korea, 에이아이에스 코리아)의 AIXM 5.1 (에이아이엑스엠 파이브포인트원) 피드**가 있는데 정부 계약이 필요합니다. 현재는 FAA SWIM (에프에이에이 스윔)에 포함된 한국 관련 NOTAM (노탐) (KR (케이알) 공항 코드 필터링)을 쓰고, 정식 AIS Korea (에이아이에스 코리아) 연동은 P9+ (피나인플러스) 로 계획되어 있습니다.

### Q6 (큐식스): "대학생이 Helm chart (헬름 차트), Terraform (테라폼), Argo Rollouts (아르고 롤아웃) 까지 배울 필요가 있나요?"

A (에이): **있습니다**. 실무에서는 모델 정확도만큼이나 **배포·운영·관측성·거버넌스**가 중요합니다. Strategic Review (스트래티직 리뷰)에서 지적한 "Engineering Package (엔지니어링 패키지)" 병목이 바로 이 부분입니다. "캡스톤 MVP (엠비피)"에서 "production-ready SaaS (프로덕션 레디 사스)"로 체급 전환하려면 이 infrastructure (인프라스트럭처)가 필수입니다. 이 프로젝트로 저는 **대학생이 아니라 실무 엔지니어 수준**이라는 포트폴리오를 만들고 싶었습니다.

### Q7 (큐세븐): "왜 XGBoost (엑스지부스트)인가요? LightGBM (라이트지비엠)이나 CatBoost (캣부스트)는요?"

A (에이): **XGBoost 2.0 (엑스지부스트 투포인트제로)**이 가장 넓은 ecosystem (에코시스템)을 가지고 있고 (MLflow (엠엘플로우)·SHAP (샤프)·vLLM (브이엘엘엠) 모두 XGBoost (엑스지부스트) first-class (퍼스트클래스) 지원), **production (프로덕션) 안정성**도 검증됐습니다. LightGBM (라이트지비엠)도 고려했는데 XGBoost (엑스지부스트) 대비 약 10% 빠르긴 하지만 **overfitting (오버피팅) 성향**이 있어서 tabular (태뷸러)에서 안정성이 떨어집니다. CatBoost (캣부스트)는 **범주형 feature (피처)가 많을 때** 강한데 저는 주로 수치형이라 이점이 크지 않았습니다.

### Q8 (큐에잇): "LoRA rank 64 (로라 랭크 식스티포)는 어떻게 정했나요?"

A (에이): rank 64 (랭크 식스티포)는 **QLoRA (큐로라) 논문 (Dettmers et al., 2023, 데트머스 외 2023)**의 7B (세븐비) 모델 기준 권장값입니다. 더 작게 (rank 16, 랭크 식스틴) 하면 성능이 떨어지고, 더 크게 (rank 128, 랭크 원투에잇) 하면 VRAM (브이램) 부족합니다. rank 64 (랭크 식스티포)가 RTX 3070 8GB (알티엑스 써리세븐티 에잇기가바이트)에서 가장 균형 잡힌 값입니다.

### Q9 (큐나인): "Conformal Prediction (컨포멀 프리딕션)의 90% coverage (커버리지)는 학습 데이터에만 유효하지 않나요?"

A (에이): **그래서 별도의 calibration set (캘리브레이션 셋)을 씁니다.** MAPIE SplitConformalRegressor (마피 스플릿컨포멀리그레서)는 훈련-calibration (캘리브레이션)-test (테스트) 3-way split (쓰리웨이 스플릿)을 쓰는데, calibration set (캘리브레이션 셋)에서 계산한 conformity score (컨포미티 스코어)가 **IID (아이아이디) 가정 하에서 test set (테스트 셋)에도 유효**합니다. 실제로 Val set (밸 셋) 72,308건에서 empirical coverage (엠피리컬 커버리지) 90.00% 나왔는데, Test set (테스트 셋)에서도 거의 동일하게 나왔습니다.

### Q10 (큐텐): "이 시스템이 실제 관제탑에 바로 배포될 수 있나요?"

A (에이): 아직은 **"Advisory Copilot (어드바이저리 코파일럿)"** 포지션입니다. 최종 의사결정은 사람이 하고, AI (에이아이)는 추천만 합니다. 실제 관제 시스템에 배포되려면 ICAO Annex 10 (아이카오 에넥스 텐) 인증, RTCA DO-178C (알티씨에이 디오-원세븐에잇씨) 소프트웨어 인증, **NIST AI RMF (니스트 에이아이 알엠에프)** 준수 등 추가 절차가 필요합니다. P8-F (피에잇-에프)에서 추가한 **human-in-the-loop approval (휴먼 인 더 루프 어프루벌)**이 이런 규제 환경을 대비한 설계입니다.

### Q11 (큐일레븐): "현재 Docker (도커) NAS (나스)에 돌리고 있다고 했는데 상용 서비스로는?"

A (에이): 네, 지금 보시는 <https://skyops.your-domain> (에이치티티피에스 슬래시슬래시 스카이옵스 닷 유어 도메인) 은 NAS (나스) Docker (도커) 기반 임시 공개입니다. 실 상용은 **ADR-003 (에이디알-003) multi-region (멀티 리전) 배포**대로 KR primary (케이알 프라이머리, asia-northeast3, 아시아 노스이스트 쓰리) + EU (이유)/US (유에스) read replica (리드 레플리카) 구조로 가게 될 겁니다. Helm chart (헬름 차트)와 Terraform (테라폼) 모듈이 이미 준비되어 있어서 **GCP GKE (지씨피 지케이이) 클러스터 있으면 15분 내 배포**가능합니다.

### Q12 (큐트웰브): "비행 단계 분류가 90.3% 정확도인데 나머지 10%는?"

A (에이): 주로 **holding pattern (홀딩 패턴)** (공항 위에서 선회 대기) 구간에서 혼동이 생깁니다. heuristic classifier (휴리스틱 클래시파이어)는 "고고도 + 저속"을 CRUISE (크루즈)로 보는데 holding (홀딩)은 실제로 APPROACH (어프로치)에 가깝습니다. P7 (피세븐)에서 ML classifier (엠엘 클래시파이어)로 업그레이드해서 이 문제를 개선했고, **P9+ (피나인플러스) 에서는 holding pattern (홀딩 패턴) 전용 feature (피처)** (sustained turn rate (서스테인드 턴 레이트) + level altitude (레벨 알티튜드))를 추가해서 95%+ 목표하고 있습니다.
